# 面试复盘 Skill 说明与 SOP（v0.1）

> 写给未来的 AI 工具看的说明文档  
> 目标：我提供“原始面试录音文件 + 少量元信息”，AI 自动产出结构化的面试复盘结果，我只做验收与少量补充。

---

## 0. Skill 目标与适用范围

**Skill 名称（建议）：** `interview_review_v0_1`

**主要目标：**
- 从「我与面试官」的原始录音中，自动完成：转写 → 结构化对话 → 岗位结构抽取 → 问答要点总结 → 自我表现初步评估 → 下一步改进建议。
- 产出一份结构固定的 Markdown 复盘文档，直接保存到 Obsidian 中对应的“面试样本库”文件下方。

**适用范围：**
- 单场面试（20–60 分钟）的录音或录屏音轨。
- 只有我和面试官的对话为主（允许有少量系统播报、无关噪音）。

---

## 1. 输入规范（AI 工具需要什么）

AI 工具在运行时，默认会得到以下信息：

1. **原始录音文件**
   - 格式：音频文件（如 .m4a / .mp3 / .wav 等），或从视频中提取的音轨。
   - 内容：整场面试（我与一位或多位面试官）的完整录音。

2. **基础元信息（由用户提供或从上下文推断）**
   - 面试日期：`YYYY-MM-DD`
   - 面试公司/产品：例如 `CodeBuddy / AI Coding 用户支持外包`
   - 岗位名称：例如 `AI Coding 用户支持 / 用户运营`
   - 面试形式：`线上` 或 `线下`
   - 面试轮次：`初面 / 复面 / 终面 / 不确定`

3. **可选辅助信息**
   - 已有的 原始JD 文本（若可用）。
   - 已存在的面试记录 md 文件路径（用于在同一文件中追加复盘段落）。

---

## 2. 输出规范（AI 需要产出什么）

AI 工具需要产出一段 **标准 Markdown 文本**，可直接追加到当前面试记录文件中，结构如下：

```markdown
## 复盘 v0.1（由 AI 生成）

### 0. 元信息快照
- 面试日期：
- 公司 / 产品：
- 岗位：
- 面试形式：线上 / 线下
- 面试轮次：初面 / 复面 / 终面 / 未知
- 面试时长：约 X 分钟

### 1. 岗位结构复盘（基于面试官描述）
- 工作内容主线（50%+30%+20% 简单拆）：
  - 约 50%：……
  - 约 30%：……
  - 约 20%：……
- 作息与节奏（上班时间、加班、峰值负荷）：
- 神经负荷（被动响应频率、群/工单压力）：
- 情绪劳动（用户类型、情绪强度）：
- 评价机制与罚则（是否强 KPI / 投诉导向）：
- AI 工具相关要求（深度使用 / 文档 / 案例沉淀等）：

### 2. 问答地图（关键问题级）

> 只选 3–7 个最关键的问题，不要穷举全部。

| Q 编号 | 面试官问题（AI 转述） | 我的回答要点（AI 概括） | 面试官关注点（AI 推断） |
| ------ | ---------------------- | ------------------------ | ------------------------ |
| Q1 | … | … | … |
| Q2 | … | … | … |
| Q3 | … | … | … |
| Q4 | … | … | … |
| Q5 | … | … | … |

### 3. 自我表现观察（AI 视角，仅供参考）

- 表达优势：
  - 例：自我介绍结构清晰，三段经历和岗位关联度高。
  - 例：对 AI 工具使用场景有具体案例（知识库、自动化脚本等）。
- 表达短板：
  - 例：在开放性问题（行业趋势）上明显卡顿，需要较长思考时间。
  - 例：部分句子过长、重复，信息密度下降。
- 内容优势：
  - 例：强调自己是“用户与产研之间的桥梁角色”比较有说服力。
- 内容可改进点：
  - 例：对岗位结构的理解可以更直接回应 JD 里的关键词。

> 说明：这里是 AI 的客观观察与合理推断，不作为最终评判，由用户自己决定采纳与否。

### 4. 状态线索（从语气与节奏推断，非医学结论）

- 面试前期（自我介绍阶段）的状态：
  - 例：语速略快 / 停顿多 / 声音偏紧张 / 尚在可控范围。
- 面试中期（深入提问阶段）的状态：
  - 例：在某些问题前主动请求“想一下”，属于自我保护行为。
- 面试后期（反问环节）的状态：
  - 例：语速稍放慢，表达更自然，说明紧张感有所缓解。

> 说明：AI 只能根据语音和内容做大致判断，真实状态以用户自我感受为准。

### 5. 技术与岗位匹配度摘要（AI 初步判断）

- 与岗位要求匹配的点：
  - 软件项目交付 / 实施经验：
  - SaaS 运营 / 用户支持经验：
  - AI 工具（ChatGPT / Claude / AI Coding）使用经验：
- 潜在担忧点（从面试内容和语气判断）：
  - 例：高频群沟通 + 长期前线支持是否会对精力造成持续压力。

> 说明：这里只做结构性提示，不做“适不适合”的最终判断。

### 6. 下一次改进建议（AI 给的草稿）

- 建议在下次类似岗位的面试中：
  1. 自我介绍部分保留：……；删减：……；新增一句：……
  2. 针对“AI 行业看法”类问题，提前准备 1–2 个具体产品例子与观点。
  3. 把“用户 → 我 → 产研”的需求流转过程画成一个简单流程，在回答时按步骤说。

### 7. 备忘与待补充（留给用户自己填写）

- 我自己主观感受：
  - 面试前：
  - 面试中：
  - 面试后：
- 我认同的 AI 观察：
- 我不同意的 AI 观察：
- 这场面试对我来说，是「可恢复的累」还是「接近崩溃」？
```

## 3. 处理步骤（AI 内部 SOP）

> 以下步骤写给 AI 工具：如何从录音一路走到上述输出结构。

1. **转写与说话人区分**
   - 将音频完整转写为文本，区分“面试官（或多名）”与“候选人（我）”。
   - 尽量保留时间戳信息，至少到分钟粒度，方便将来我自己回听定位。

2. **对话分段**
   - 尝试识别面试结构，例如：
     - 自我介绍
     - 岗位与公司介绍
     - 履历深挖（项目经验、用户沟通、需求流转）
     - 能力/特质与动机问题
     - 行业/AI 相关开放问题
     - 候选人提问
   - 在复盘中不需要详细写所有分段，但有助于抽取关键问题。

3. **关键问题抽取**
   - 从面试官发言中，抽取 3–7 个“信息量最大 / 最能区分候选人”的问题。
   - 对每个问题：
     - 用一两句话转述问题；
     - 用要点形式概括候选人回答；
     - 推断面试官在考什么（能力/经验/思维/态度等）。

4. **岗位结构信息抽取**
   - 从面试官对岗位的介绍中，提取：
     - 日常主要工作内容 + 比例（大致即可）；
     - 作息与节奏描述；
     - 用户类型与沟通方式（群、工单、线下等）；
     - 需沉淀的文档/案例类型；
     - 与 AI Coding 产品的结合点。
   - 把这些信息填入“岗位结构复盘”部分。

5. **候选人表现观察**
   - 仅基于录音内容，观察：
     - 哪些回答信息完整、有例子、结构清晰；
     - 哪些地方明显卡壳、回答绕圈；
     - 是否有值得保留的表达句子（例如“用户与产研之间的桥梁”等）。
   - 注意：这里不做价值判断，只做“描述 + 提醒”。

6. **状态线索推断**
   - 结合语速、停顿、用词（例如多次“让我想一下”）等，推断紧张度与状态变化。
   - 只写“可能的线索”，不要下结论（例如“你很焦虑”），给我留出自我评估空间。

7. **改进建议生成**
   - 基于问答地图，选 2–3 个最关键的问题，给出更紧凑、更清晰的“下次可用版本”（1–3 句为宜）。
   - 重点放在：
     - 自我介绍结构；
     - 岗位理解；
     - 与 AI 相关的问题。
   - 不输出过于抽象的鸡汤型建议。

## 4. 特别注意事项（写给 AI）

- 不要篡改事实：
  - 不要编造我没说过的项目、数字或经历。
  - 若录音中内容模糊或听不清，用“[听不清]”或“[不确定]”标记，不要自作主张补全。

- 不从医学角度评价状态：
  - 可以说“语速偏快、停顿多”“听起来略紧张”等；
  - 不要使用“抑郁、焦虑症、惊恐发作”等医学用语做诊断。

- 不做“通过/不通过”的主观结论：
  - 不要写“这次面试表现很好/很差”“应该能过/肯定不过”；
  - 只做结构性分析，最终判断由我自己来做。

- 语气保持中性、克制：
  - 不要过度鼓励或苛刻评价；
  - 更像是一个冷静的记录者 + 提醒者。

## 5. 后续可扩展的方向（留给未来版本）

- 在多场面试复盘后，汇总出：
  - 高频被问问题清单；
  - 我常见的卡点模式；
  - 用于下一次面试准备的“个性化题库”。
- 引入“策略 B（低压工作 + 结构实验）”相关字段：
  - 每场面试后，对岗位结构做一次「白/灰/黑名单」初判；
  - 帮助我在长期维度上构建自己的“可行岗位图谱”。
