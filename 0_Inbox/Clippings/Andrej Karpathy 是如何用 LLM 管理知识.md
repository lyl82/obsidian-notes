AI大神 Andrej Karpathy 是如何用 LLM 管理知识的？最近（2026年4月2日），Karpathy 在 X 上详细分享了他正在使用的个人知识管理系统。核心思路是：不再让 LLM 只是“聊天机器人”，而是把它变成一个知识编译器 + 维护者 + 查询引擎。把散乱的研究资料（论文、文章、代码、图片、数据集等）自动编译成一个结构化的、像代码仓库一样的 Markdown Wiki（用 Obsidian 查看），整个过程几乎不需要手动编辑，LLM 全权负责编译、查询、输出和自我修复。他目前一个研究主题的知识库已经达到 ~100 篇文章、约 40 万字，完全不需要复杂的 RAG（Retrieval-Augmented Generation），LLM 就能轻松处理复杂问题。下面逐条详细解释你列出的 7 个步骤（完全对应 Karpathy 的实际 workflow）：1. 数据采集 → 散乱的来源变成一个干净的 raw/ 目录
- 你把所有原始资料统一丢进一个叫 raw/ 的文件夹（像代码仓库的 src/ 一样干净）。
- 来源可以是：PDF 论文、网页文章、GitHub Repo、数据集、图片、视频截图等。
- 实用技巧（Karpathy 自己用的）：
	- 用 Obsidian Web Clipper 浏览器插件，一键把网页文章转成干净的 Markdown 文件。
		- 同时用热键把文章里的所有图片自动下载到本地（这样 LLM 就能直接引用图片，不用依赖外部链接）。
- 结果：所有原始数据都被本地化、标准化，变成 LLM 能轻松读取的结构化输入。以后无论来源多乱，都统一扔进 raw/ 就行。
2\. LLM 编译 → 原始数据变成有结构的 wiki（摘要、概念、链接、索引全自动生成）
- 这步是整个系统的核心：你让 LLM（比如 Claude 或 GPT-4o 等前沿模型）增量编译 raw/ 里的内容。
- LLM 会自动生成：
	- 每篇文档的摘要（Summary）
		- 核心概念文章（Concepts）：把相同主题的内容合并成一篇独立的.md 文章
		- 双向链接（Backlinks）：自动在相关文章间建立链接
		- 索引文件（Index）：自动维护整个知识库的目录、标签、搜索索引
- 整个 wiki 就是一个文件夹 + 大量.md 文件的集合，结构清晰、可版本控制（Git）。
- LLM 像“编译器”一样工作：输入原始数据 → 输出结构化、可编程的知识图谱。Karpathy 强调，他几乎不手动编辑 wiki，全部交给 LLM。
3\. Obsidian 查看 → 不用终端，所有知识像代码仓库一样可浏览
- Obsidian 作为“前端 IDE”（他称之为 IDE frontend）。
- 你可以在 Obsidian 里同时看到：
	- raw/ 原始资料
		- 编译后的结构化 wiki
		- 各种可视化图表（通过插件）
- Obsidian 的优点：纯 Markdown、本地文件、支持双链、图谱视图、插件生态（比如 Marp 做幻灯片）。
- 知识库看起来就像一个代码仓库：你可以浏览、搜索、跳转，完全不需要敲终端命令。Karpathy 说：“所有知识像代码仓库一样可浏览”——这正是他想要的“可编程”感觉。
4\. LLM 问答 → 对 40 万字的知识库提复杂问题，LLM 自己去查阅和研究
- 知识库够大后（他举例 ~40 万字），你直接问 LLM 复杂问题：
	- “基于这些论文，总结 XX 技术的演进路线，并指出当前最大的 open problem”
		- “比较 A、B、C 三种方法的优缺点，并给出我的下一个实验建议”
- LLM 自动去 wiki 里查阅：
	- 它自己维护了索引和摘要，能快速定位相关文档
		- 读取完整上下文，进行深度研究（research）
		- 不需要你手动提供 RAG 检索，它像“研究助手”一样自己翻资料
- 这步让 LLM 从“一次性聊天”变成了长期记忆 + 研究引擎。
5\. 输出 → 答案不是聊天记录，而是.md / 幻灯片 / 图表等可复用的文件
- 关键区别：LLM 不再只给你一段聊天文本，而是输出可复用的文件。
- 支持的输出格式（Karpathy 已经在用）：
	- .md 笔记文件
		- Marp 格式的幻灯片（直接在 Obsidian 里预览/导出 PPT）
		- Matplotlib / 代码生成的图表（图片）
		- 其他可视化输出（未来可以扩展）
- 你直接在 Obsidian 里打开这些文件，就像打开代码文件一样。输出不再是“一次性消费”，而是可版本、可复用、可分享的资产。
6\. 归档回流 → 每次探索的输出沉淀回 wiki，知识越查越厚
- 每次 LLM 生成的笔记、幻灯片、图表、分析报告，都自动归档回 wiki。
- 结果：知识库越用越厚、越用越聪明。
- 你的每一次探索、每一次提问，都在为知识库“添砖加瓦”。这形成了正反馈循环：查询 → 输出 → 沉淀 → 下次查询更强。
- Karpathy 说：“我的探索和查询总是会‘累加’到知识库里。”
7\. 校验 (linting) → LLM 自检不一致、补缺失、发现新关联，知识库自我修复
- LLM 定期运行“健康检查”（health checks / linting）：
	- 找出数据不一致的地方
		- 补全缺失信息（可以调用网页搜索工具）
		- 发现新关联，建议生成新的概念文章
		- 提出“接下来应该深入研究哪些问题”
- 这让知识库拥有自我修复能力，就像代码有 linter + CI 一样。
- 整个系统变成了活的、不断进化的知识体，而非静态文档。

LLM lint（或 LLM Linting） 是 Karpathy 知识管理系统里非常重要的一个环节，简单来说就是：让 LLM（大模型）像程序员用“lint 工具”检查代码一样，去自动检查和修复你的整个知识库（wiki）。先理解传统“Lint”是什么在软件开发中：
- Lint 是一个工具（比如 ESLint、markdownlint、pylint 等），它会扫描你的代码或文档，找出：
	- 语法错误
		- 风格不一致
		- 潜在 bug
		- 缺失的部分
		- 坏的实践
- 目的：让代码更干净、更可靠、更一致，而不需要程序员手动一行一行检查。
LLM lint 是什么？（Karpathy 的用法）Karpathy 把这个概念搬到知识管理上，用 LLM 代替传统 lint 工具，来维护他的 Markdown wiki 知识库。LLM lint 的核心作用就是让知识库拥有自我修复和自我改进的能力。具体会做这些事情（完全对应他分享的内容）：
- 找出不一致的地方（Inconsistencies）：  
	同一个概念在不同页面里说法矛盾？同一个事实在两篇总结里数据不一样？LLM 会指出来。
- 发现缺失的信息（Missing data）：  
	某个重要概念缺少关键细节、缺少最新论文引用、缺少比较表格等。LLM 会标记出来，甚至建议补充（可以结合网页搜索工具自动补全）。
- 发现新关联（New connections）：  
	LLM 读完整个 wiki 后，会主动说：“这两个概念其实可以建立新链接，我建议创建一个新的概念页面，把它们关联起来。”
- 提出改进建议：  
	“这个索引文件过时了，需要更新”；“某些页面缺少双向链接”；“知识库里缺少某个子主题的时间线”。
- 整体健康检查（Health checks）：  
	定期跑一次，让 LLM 对整个 40 万字的知识库做一次“体检”。
他把这个过程叫做 “System linting” 或 “LLM health checks”。LLM lint 在整个系统里的位置（第7步）回忆你最初列的7个步骤：
1. 数据采集（raw/）
2. LLM 编译 → 生成结构化 wiki
3. Obsidian 查看
4. LLM 问答
5. 输出可复用文件
6. 归档回流（把新输出沉淀回 wiki）
7. 校验 (linting) → LLM 自检、补缺失、发现新关联，知识库自我修复
Linting 是让系统“活起来”的关键。没有 linting，wiki 只是静态文档堆积；有了 linting，知识库就会自动变好、越用越聪明。它和第6步“归档回流”形成正循环：
- 你查询 → LLM 输出新知识 → 回流到 wiki
- 定期 linting → 发现问题并修复 → 知识库质量提升 → 下次查询结果更好
实际怎么操作 LLM lint？（最简单方式）和“编译 wiki”类似，你可以用两种方式：1. 最简单：直接用 Chat 界面（Claude / GPT 等）
- 把你的 wiki/index.md（总目录） + 几篇核心概念页面内容复制给 LLM。
- 使用类似下面的提示：

```
你现在是我的知识库 lint 工具。
请对整个提供的 wiki 内容进行健康检查：
1. 找出所有事实不一致或说法矛盾的地方
2. 指出哪些概念缺少关键信息，并建议补充什么
3. 发现可以建立新关联的概念，建议创建新页面
4. 检查索引和链接是否需要更新
5. 输出需要修复或新增的文件完整 Markdown 内容

只基于我提供的内容，不要编造信息。
```
